# תוכנית בדיקות – MVS, אלפא סגורה (MVP)

מבוססת על `docs/spec.md` (מקור האמת) ועל הכרעות סקירת מנהל המוצר (ש-*, PR #6). גרסה 2, 2026-11-03.

שם המוצר: **MVS** (יומן, שורה 27). "MVP" כאן הוא שם השלב.

## מטרה והיקף

לוודא שהאלפא הסגורה עומדת בדרישות ה-MVP ובקריטריוני ההצלחה מהאפיון, על
Windows, macOS ו-Linux, לפני שמזמינים בודקים. Web, קול, DM, קבצים ורולים
מלאים – מחוץ להיקף (שלבים 2 ומעלה).

**קריטריוני ההצלחה של ה-MVP (מהאפיון) – כל אחד הוא מקרה בדיקה (SC-01–SC-04):**

1. 3 מחשבים ברשתות שונות ובשלוש מערכות הפעלה מצטרפים בלינק ורואים את אותן הודעות.
2. הודעה מגיעה תוך פחות משנייה כשכולם מחוברים.
3. היוצר סוגר את האפליקציה – שני האחרים ממשיכים לדבר.
4. מי שהיה offline מקבל את מה שפספס כשהוא חוזר.

## סביבות

| סביבה | שימוש |
| --- | --- |
| Docker (Playwright 1.56.1, Chromium) מול ה-UI עם ה-mock core | בדיקות smoke ו-explore אוטומטיות, בכל PR |
| Docker (`rust:1.90-bookworm`) | `cargo test`, `qa/core/cli-checks.sh`, harness של sync |
| מחשבים אמיתיים: Windows 11, macOS (Intel + Apple Silicon), Ubuntu / Fedora | בדיקות ידניות, התקנה, עדכון, NAT, ביצועים |
| רשתות: סיב ביתי, נקודה חמה סלולרית, רשת עבודה עם חומת אש | חציית NAT ו-relay |
| מחשב ייחוס לביצועים: 4 ליבות, 8GB, SSD | כל יעדי ביצועי הממשק |

## חומרה וסיווג באגים

- **חוסם** – אובדן נתונים או זהות, עקיפת אבטחה, תהליך ראשי שלא עובד. אין שחרור.
- **גבוה** – תהליך ראשי עובד רק בעקיפה, או יעד ביצועים מוחמץ בהרבה.
- **בינוני** – התנהגות שגויה שבודק ייתקל בה, או דרישת אפיון שלא מולאה.
- **נמוך** – קוסמטי או מקרה קצה.

כל באג נרשם ב-`qa/BUGS.md` עם צעדים, צפוי מול בפועל ובעלים (ui, sync,
records/authority, updater).

## קריטריוני כניסה ויציאה

**כניסה:** build חתום לכל פלטפורמה; `cargo test` ו-smoke ירוקים; שרת ה-relay רץ.

**יציאה (Definition of Done מהאפיון):** כל המקרים בעדיפות 1 עברו בשלוש
מערכות ההפעלה; אין באג חוסם או ממצא אבטחה חוסם פתוח; smoke ו-explore ירוקים;
יעדי הביצועים נמדדו ונרשמו; SC-01–SC-04 עברו.

## סימון אוטומציה

- **אוטומטי** – קיים היום ב-`qa/` (ציון הקובץ).
- **ניתן לאוטומציה** – אפשר לכתוב עכשיו או כשהליבה האמיתית תחובר (Playwright מול Tauri, harness של sync, בדיקת Rust).
- **ידני** – דורש חומרה, רשת אמיתית או שיפוט אנושי.

עדיפות: 1 = חייב לפני האלפא, 2 = רצוי, 3 = אם יש זמן.

## מה כבר אוטומטי ואיך מריצים

ראו `qa/README.md`. בקצרה: `smoke` (8 בדיקות, מסלול ההצלחה) ו-`explore`
(46 בדיקות, כולל שחזור של כל באג UI פתוח ב-`BUGS.md`, UX-01, פריסת טלפון ונתונים עוינים) רצים ב-Docker מול ה-UI;
`qa/core/cli-checks.sh` בודק את ה-CLI של updater ו-spike-peer עם קלט שגוי
ו-manifest מזויף.

## סיכונים לבדיקות

- ה-UI רץ היום מול mock core: כל מה שמסומן "ניתן לאוטומציה" מול הליבה
  האמיתית ייכתב כשה-adapter של Tauri יחובר. אותן בדיקות Playwright אמורות
  לרוץ גם אז, בשינוי של כתובת ההפעלה בלבד.
- בדיקות NAT תלויות בבודקים חיצוניים ברשתות שונות – לתאם מראש.
- יעדי ביצועים נמדדים ב-Docker על מחשב חזק מהיעד; המדידה המחייבת – על
  מחשב הייחוס.
